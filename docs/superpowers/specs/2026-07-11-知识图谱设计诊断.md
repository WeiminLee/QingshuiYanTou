## 0. 一句话结论

**知识图谱设计存在缺陷，而且根子上的缺陷不是"某个 Schema 选得不好"，而是——设计文档、实体 ID 生成、关系模型三者已经分裂成两套甚至三套并存的半成品；大量核心功能处于"静默失败"状态，系统却对上层报告成功。**

四条铁律的落地情况：

| 铁律 | 状态 | 主要违背点 |
|------|------|-----------|
| 正交性（实体各司其职） | ❌ 破坏 | 所有公司塌缩到主体 ts_code 节点（B1）；typed 与无类型关系双模型并存（A2） |
| 时序性（只追加不覆盖历史） | ❌ 破坏 | `valid_from=today()` 伪造时序跃迁（C1）；批量 upsert 篡改历史边（C2）；合并 `DETACH DELETE`（C3） |
| 可溯源性（每边绑 source+weight） | ❌ 破坏 | 合并把多源边折叠成一条（C3）；weight 语义反转（F1）；写入失败不上报（D4） |
| 克制扩展（最小 Schema） | ❌ 侵蚀 | 两套 ID 生成器、两个 chunker、三张置信度表、残留已删实体类型（A1/A3） |

## 2. 六个根因主题

发现被收敛为 6 个根因主题。**A 是母缺陷**：正因为存在双轨模型，才衍生出 B/C/D 里一连串"字段名对不上、ID 对不上、边被折叠"的具体 bug；**D（静默失败）是这些缺陷长期没被发现的原因**。

```
A 双轨漂移（母缺陷）
├─ B 实体身份不稳 → 重复节点 / 节点塌缩
├─ C 时序 / 可溯源铁律未落地
├─ D 静默失败，失败被当成功
├─ E 检索 / 摘要层与图谱不一致
└─ F 抽取质量护栏薄弱
```

---

### 主题 A — 设计 / 实现双轨漂移（🔴 母缺陷）

设计文档描述的是一套"理想 Schema"，代码里却同时活着旧版和新版两套实现，谁是权威无从判断。

| 编号 | 严重度 | 位置 | 问题 |
|------|--------|------|------|
| **A1** | 🔴 Critical | `entity_id.py:43-58,199` vs `entity_service.py:66-104` vs `docs/知识图谱设计.md:41,66,88` | **两套 ID 生成器 + 与文档三方不一致**。文档写 `CO:300308_SZ`/`PROD:`/`MT:`；`entity_service.generate_entity_id`（主管线用）出 `C:300308.SZ`/`P:`/`M:{ts}:{metric}:{period}`；`entity_id.entity_id_from_name`（另一套）出 `C:`/`P:{hash}`/`M:{hash}`。前缀、大小写、Metric 方案全不一致。 |
| **A2** | 🔴 Critical | `relation_types.py:9-29`、`relation_service.py:188/745`、`state_writer.py:75`、`contradiction.py:171` | **有类型 / 无类型两套关系模型同图并存**。文档 §3.5 要求"统一 RELATES"，实际图里同时有 `:RELATES`（主抽取用）、17 种 typed 边（`upsert_relation`/API 用）、`:CONTRADICTS`、`:STATE_TRANSITION`。typed 边存 `confidence`，RELATES 边存 `weight`，字段都分裂。 |
| **A3** | 🟡 Medium | `entity_id.py:50-57`、`extraction/chunker.py` vs `ingestion/chunker.py`、`confidence.py:49` vs `evidence.py:119` | **残留已删 Schema + 重复实现**。`entity_id_from_name` 仍生成 `T:`(Tech)/`IND:`(Industry)/`E:`(Event)，而文档 §2.1 已删这三类；两个语义不同的 chunker（1024 token vs 6000 token）；三张互相矛盾的置信度表。 |

> **影响**：A 使得"这个系统到底遵循哪一版设计"无法回答。任何修复若不先统一这条主线，都会在另一条轨上复活。

### 主题 B — 实体身份不稳 → 重复节点 / 节点塌缩（🔴）

实体 ID 是节点身份的唯一锚。这里的缺陷让"同一实体多个节点"和"多个实体一个节点"同时发生。

| 编号 | 严重度 | 位置 | 问题 |
|------|--------|------|------|
| **B1** ✅ | 🔴 Critical | `kg_extractor.py:146` + `entity_service.py:82-86` | **所有公司塌缩到主体 ts_code 节点**。`_build_name_to_id_map` 对文档里**每个** Company 都传入主体 `ts_code`，`generate_entity_id` 对 Company 只要 ts_code 非空就返回 `C:{ts_code}`、忽略公司名。结果：一篇研报里客户/供应商/竞争对手全部拿到同一个 `C:{主体代码}` → 供应链关系退化为主体对自身的自环，`ON MATCH SET n.name` 还会用最后一个公司名覆盖主体名。`irm_extractor.py:51-58` 有同样缺陷。**注意**：`entity_id.py:131` 的 `build_name_to_id_map`（逐个 `resolve_company_id`）才是正确实现，但主路径没用它。 |
| **B2** | 🔴 Critical | `entity_resolver.py:406-448`（`_migrate_relationships` / `apply_merges`） | **实体合并整体失效或摧毁溯源**。`MERGE (c:Entity {entity_id})` — 真实节点标签是 `Company/Product/Metric`，从无 `:Entity` 标签 → 找不到已存在节点会 CREATE 空壳；`MERGE (c)-[r2]->(b)` 无类型 MERGE 是**非法 Cypher**（Neo4j 要求恰好一个关系类型）→ 抛异常被吞 → 合并静默失败。即便成立，`MATCH (a)-[r]->(b)` 的多条不同 source 边会被折叠成一条 → 破坏可溯源性。合并还从不并入被删节点属性，直接 `DETACH DELETE`。 |
| **B3** | 🟠 High | 全仓 Neo4j 无 `CREATE CONSTRAINT`；`relation_service.py:820-828` | **无唯一约束 + TOCTOU 竞态**。`upsert_entity`/`upsert_relates` 靠应用层"先查后写"保证幂等，但存在性检查在独立会话、写入在另一事务，两个写者都看到"不存在"→ 都 CREATE → 重复节点/重复边。alembic 里的约束全是 Postgres 表，与 Neo4j 图无关。 |
| **B4** | 🟠 High | `kg_extractor.py:588` vs `146` | **命中 / 未命中两条路径 ID 不同**。写入时 lookup 未命中就用不带 ts_code/period 的回退 ID → 与建 lookup 时的 ID 不同 → 同一实体两个节点。lookup 键用 `name`/`name.lower()`，任何归一化差异即 miss。 |

### 主题 C — 时序 / 可溯源铁律未落地（🔴）

文档 §六要求"只追加不覆盖历史"，实现却在多处覆盖、篡改、伪造历史。

| 编号 | 严重度 | 位置 | 问题 |
|------|--------|------|------|
| **C1** | 🔴 Critical | `relation_service.py:794-795,946-960` + 全抽取路径无幂等守卫 | **重复运行伪造时序跃迁**。RELATES 的 `valid_from` 默认 `date.today()`。同一份文档隔天重抽 → `valid_from` 变新日期 → 命中不到旧边 → 走新建分支 → 把昨天的边 `valid_to=前天` 再插新边。数据没变却凭空生成"失效→新生效"。`valid_from` 应取文档/公告日期而非 today。 |
| **C2** | 🟠 High | `relation_service.py:564-601`（`batch_upsert_relations_unwind`） | **批量路径篡改已封存历史边**。MERGE 键丢了 valid_from，Stage 1 先把开放边关闭，Stage 2 的 `MERGE (a)-[r:RELATES]->(b)` 又匹配到刚关闭的历史边走 ON MATCH → 在 `valid_to != null` 的历史边上追加 descriptions、抬 weight。与单条 `upsert_relates` 语义分叉（`scripts/expand_sector_v1_2.py` 在用批量版）。 |
| **C3** | 🟡 Medium | `entity_resolver.py:386-403,441-448` | **合并跨事务 + 丢属性**。`_migrate_relationships` 与 `_delete_entity` 非同一事务，迁移成功删除失败 → 孤儿节点；被删节点的 `properties/aliases/raw_names` 直接 `DETACH DELETE` 抹除。 |
| **C4** | 🟡 Medium | `extraction/chunk_dedup.py:57-93` | **去重模块写了却没接入**。`find_new_chunk_indices` 按下标 `zip` 比对（开头插一段 → 后续全平移全判变更），且 `kg_extractor` 根本没 import 它 → 抽取管线零增量、零幂等，放大 C1。 |

### 主题 D — 静默失败，失败被当成功（🔴）

本主题是全报告最危险的一类：核心功能从不工作，但全部被 `try/except → warning` 吞掉，上层状态机标记 `done`。

| 编号 | 严重度 | 位置 | 问题 |
|------|--------|------|------|
| **D1** ✅ | 🔴 Critical | `state_writer.py:70-99` | **STATE_TRANSITION 边从未写入**。Cypher 字符串里用了 `#` 注释（Cypher 只认 `//`）+ map 字面量尾逗号 → 必然语法报错 → 被 `except` 吞。这条边被 `relation_types.py:40` 自注为"最重要"，实际图里零条。 |
| **D2** | 🔴 Critical | `entity_resolver.py:400-401` | **实体合并永不生效**（同 B2 的运行时后果）：非法 MERGE 抛异常被 `try/except` 吞 → `merged_count` 永远不增，日志显示"合并 N 对"但图没变。 |
| **D3** ✅ | 🟡 Medium | `contradiction.py:105` vs `relation_service.py:804,847` | **多源冲突检测永不触发**。读历史边的 `relation_description` 字段，RELATES 边实际存 `text`/`descriptions`，取值恒空 → `continue` → 冲突永不生成，`conflict_alerts` 长期为空却无人知。 |
| **D4** | 🟠 High | `kg_extractor.py:640,731,1047,1143,1473` | **写入失败不计入返回值**。每个实体/关系 upsert 是 `try/except→warning→continue`，最终 task 只统计 created+updated 后 `mark_done`，失败数不进返回值/状态。一份文档 80% 实体入库失败也显示成功。 |
| **D5** | 🟠 High | `signal_extractor.py:441-549` | **信号写入无去重 + 非原子 + 节点缺失谎报成功**。读改写非事务，每次重跑无条件追加 → `n.signals` 数组无界膨胀；节点不存在时 `MATCH...SET` 是 no-op，仍返回 `written=len(signals)`。另 `persist_signals_to_neo4j` 引用已删除的 `upsert_event` 死代码。 |

### 主题 E — 检索 / 摘要层与图谱不一致（🟠）

图谱之上的 L1/L2/L3 摘要 + 向量检索层，与底层图谱存在多处不同步与承诺未兑现。

| 编号 | 严重度 | 位置 | 问题 |
|------|--------|------|------|
| **E1** | 🟠 High | 全层无 `WHERE r.weight >= 0.5`；`summary_aggregator.py`、`vector_client.py:855`、`knowledge_package.py:304` | **文档承诺的 weight>=0.5 过滤根本没实现**。所有摘要 Cypher 只 `ORDER BY r.weight DESC LIMIT N`，向量检索无 score 阈值，知识包只按 `valid_to IS NULL` 过滤。低权重/被 reject 到近 0 的边直接进摘要污染下游。 |
| **E2** | 🔴 Critical | `vector_client.py`（只有 `delete_collection`）、`vector_ops.py:264`（stub） | **节点删除/合并后向量残留**。向量层无按 point 删除的 API；唯一对账任务 `reindex_missing_vectors` 是 `return 0` 空实现。合并/删除后 `uuid5(旧id)` 向量永久残留且仍被检索命中。 |
| **E3** | 🔴 Critical | `summary_invalidator.py:65`、`summary_cache.py:146,178-244` | **失效静默失败 + 传递性缺口 → 读到 stale 摘要**。失效整段包在 `try/except→warning`，Neo4j 抖动即不失效；读路径命中 Redis 时 `is_stale=False` 直接返回旧值。L3 内嵌多跳邻居 L2，但失效只传一跳 → 以其它产品为锚的 L3 从不失效。 |
| **E4** | 🟠 High | `feedback_service.py`（无 `trigger_invalidation` 调用） | **分析师反馈改 weight 后不触发失效**。人工纠错是最高优先级失效信号，却让 L1/L2/L3 + 向量继续反映旧权重。 |
| **E5** | 🟠 High | `knowledge_package.py:49-51,212-264` | **`CONTAINS ts_code` 跨股串味 + 伪造置信度**。`entity_id CONTAINS "300308"` 命中 `C:3003080` 等别家实体；`_build_confidence_summary` 把置信度钉死 `TIER2` 且 score = `60+数量*2`，与来源可靠性无关。 |
| **E6** | 🟠 High | `summary_aggregator.py:44-65` | **L1 锚点名选错**。L1 查邻居 n 却在邻居里找 Company 标签取名，常规情况 `company_name` 停留在原始 ID，存在公司↔公司关系时会取到**邻居公司**名 → 画像张冠李戴。 |

### 主题 F — 抽取质量护栏薄弱（🟠）

| 编号 | 严重度 | 位置 | 问题 |
|------|--------|------|------|
| **F1** | 🔴 Critical | `rag_extractor.py:661-673` + `kg_extractor.py:296` | **weight 语义反转**。合并阶段把每 chunk 置信度**累加**（3 chunk → 3.0），归一化 `raw/10`（3.0→0.3）。**被多处证据确认的关系反而得低分**，只出现一次的得 1.0。下游 weight>=0.5 过滤会系统性丢掉最可靠的多源关系。 |

## 4. 关键判断与修复优先级建议（仅建议，本轮不改动）

优先级排序的逻辑：**先止血"静默失败"让问题可见 → 再统一双轨主线 → 最后补数据库层兜底**。

1. **D 类先行**（让失败可见）：修 `state_writer.py` 的 Cypher（D1）、把 upsert 失败计数纳入返回值与状态（D4）、修冲突检测字段名（D3）。这些是"改一行就能让隐藏故障浮现"的高杠杆点。
2. **B1 紧急**（数据正在被污染）：`_build_name_to_id_map` 对非主体 Company 不得传主体 ts_code，改用 `entity_id.py` 已有的正确实现；irm_extractor 同步。**每多跑一天抽取，塌缩的脏节点就多一批。**
3. **A 主线统一**：确定唯一权威的 ID 生成器 + 唯一关系模型（RELATES 无类型 or typed，二选一），删除另一套；同步更新设计文档，消除文档/代码漂移。
4. **C + B3 时序与幂等**：`valid_from` 取文档日期；接入内容指纹幂等（对齐 irm checkpoint）；给 Neo4j `entity_id` 加唯一约束从数据库层兜底。
5. **E + F 检索质量**：实装 weight 过滤、向量删除/对账、反馈联动失效；weight 合并改 `max`/来源加权；公告全文抽取。
