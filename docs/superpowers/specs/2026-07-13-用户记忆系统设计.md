# 用户记忆系统 设计规格（Spec）

**日期**：2026-07-13
**范围**：清水投研系统 agent 的**用户记忆系统**（承接用户画像、板块/概念偏好、其他合理记忆信息）
**性质**：设计规格，供 make-plan → TDD 实现。
**不在本轮范围**：信号系统（预期差）——独立的下一轮；知识图谱层——已单独诊断。

---

## 1. 背景与问题

清水投研系统是多用户投研 agent。用户在长期交互中会形成**画像、偏好、关注点**，需要记忆系统承接，并在 agent 运行任务时注入上下文。

现有实现（`backend/app/reasoning/langchain_agent/memory/`，470 行）方向正确但有**根本缺陷**：

| 缺陷 | 证据 | 后果 |
|------|------|------|
| 记忆主键错误 | `builtin_provider.py:47,90,147` 把 `thread_id` 当 `session_id` 又当 `user_id` | 记忆绑在单次会话，换会话即丢，**用户级长期记忆从未打通** |
| user_id 未进 agent | `agent.py` 的 6 个 Request 模型只有 `thread_id`，无 `user_id` | 无法按用户隔离记忆 |
| 无结构化偏好 | 只有 profile（文本）+ notes（列表） | 无法表达"用户对某板块/概念的偏好" |
| portfolio 未利用 | `account/services/portfolio_service.py` 有持仓表，未注入 agent | 白白浪费"用户关注哪些股"的结构化信号 |
| 召回无排序 | `builtin_provider.py:57-71` 全量取出 | 记忆多时靠截断硬扛（本场景记忆量小，可接受） |

### 设计目标（YAGNI 边界）

- ✅ 多用户，按 `user_id` 跨会话共享
- ✅ 结构化承接"对板块/概念的偏好"
- ✅ 简单：**无 embedding、无向量库、无 LLM 记忆演化**
- ❌ 不做：语义检索、记忆自动进化、Zettelkasten 互联、每轮 LLM 自动抽取（仅留接口）

### 设计依据（开源调研结论）

调研了 5 个开源记忆框架（A-mem / mem0 / agentmemory / llm_wiki / 现有骨架），结论：

- **不引入任何框架**——记忆量小（每用户几十条）、需求单一，重型框架错配。
- **偷三个轻量点**：mem0 的"检索已有 + 一次 LLM 抽取"思路（本轮仅留接口）、agentmemory 的 **Jaccard 去重**（纯字符串、无 LLM）、mem0 的 **user_id 单标签隔离**。
- **强旁证**：mem0 在 2.0 版亲手砍掉了"LLM 决定 ADD/UPDATE/DELETE"机制（慢、贵、易误删）——印证"不做复杂记忆演化"是对的。

## 2. 架构

保留现有 `MemoryProvider` / `MemoryManager` 抽象与生命周期钩子，**只重写 `BuiltinProvider` → `UserMemoryProvider`**。增量演进，非推倒重来。

```
API 层 (agent.py)
  ChatRequest / V2ChatRequest 等 +新增可选 user_id 字段
        │ user_id 透传（缺省回退默认用户）
        ▼
run_lead_agent (client.py)
  MemoryManager.initialize_all(user_id)   ← 传 user_id 而非 thread_id
    ├─ prefetch_all(query) ─→ 注入 system prompt
    └─ handle_tool_call ────← manage_memory 工具
        ▼
UserMemoryProvider (重写)
  按 user_id 读写 MongoDB：profile / preferences / notes
  + portfolio（只读，从 account 库借）
  + Jaccard 去重
  + sync_turn 钩子（留接口，本轮空实现）
```

### 2.1 user_id 打通策略（渐进兼容）

- API 各 Request 模型新增**可选** `user_id: str | None`。
- 缺省时回退到默认用户：取 `users.yaml` 中第一个 `user_id`（当前为 `lwm`）；文件缺失或为空时用硬编码兜底常量 `"default"`。逻辑集中在单一解析函数 `resolve_user_id`，便于将来收紧为必填。
- `run_lead_agent` 及相关调用把 `user_id` 传入 `MemoryManager.initialize_all(user_id)`。
- 前端接入带 `user_id` 作为**后续独立小任务**，不阻塞本轮后端交付。

## 3. 数据模型

四类数据，全部以 `user_id` 为主键。MongoDB 存储（沿用现有 `get_mongo_db()`）。

### 3.1 `agent_profile` — 用户画像（1 文档/用户）
```json
{
  "user_id": "lwm",
  "profile": "偏好科技成长股，重视产业趋势与景气度，风险偏好中性偏高，不喜欢追高",
  "updated_at": "2026-07-13T10:00:00Z"
}
```
- 一段自由文本，慢变，覆盖式更新。

### 3.2 `agent_preferences` — 结构化板块/概念偏好（核心新增）
```json
{
  "user_id": "lwm",
  "items": [
    {
      "id": "8f3a1b2c",
      "subject": "光模块",
      "subject_type": "sector",
      "stance": "看好",
      "reason": "AI算力需求拉动，景气度高",
      "created_at": "2026-07-13T10:00:00Z",
      "updated_at": "2026-07-13T10:00:00Z"
    }
  ]
}
```

字段约束：

| 字段 | 类型 | 约束 |
|------|------|------|
| `id` | str | uuid4 前 8 位 |
| `subject` | str | 必填，概念/板块/个股名，归一化去空格 |
| `subject_type` | str | 枚举：`sector` / `concept` / `stock`，默认 `sector` |
| `stance` | str | 枚举：`看好` / `看空` / `关注` / `回避`，必填 |
| `reason` | str | 可选，一句话依据，≤100 字 |
| `created_at` / `updated_at` | str | ISO8601 UTC |

### 3.3 `agent_notes` — 自由笔记（其他合理记忆）
```json
{
  "user_id": "lwm",
  "entries": [
    {"id": "a1b2c3d4", "content": "用户提到年底前想减仓", "category": "general", "created_at": "..."}
  ]
}
```
- 沿用现有结构，主键换成 `user_id`。

### 3.4 portfolio — 持仓（只读，不新建集合）
- 从现有 `portfolio_service.list_for_user(user_id)` 读，**只读不写**，仅在 prefetch 时拼入上下文。
- 权威数据属 account 模块，记忆系统借用不复制，避免双写不一致。

## 4. 写入与去重

### 4.1 写入路径
`manage_memory` 工具 → `UserMemoryProvider.handle_tool_call` → 按 `target` 写对应集合。

**保留现有 guardrail**：写入前经 `filter_research_memory_text`（`builtin_provider.py:193-197`）过滤 prompt 注入内容，命中则拒绝。

### 4.2 去重规则

- **preferences（按 subject 精确匹配）**：写入 `preference` 时，先在该用户 items 中按归一化 `subject` 精确匹配：
  - 命中 → **更新**该条（stance / reason / updated_at），不新增。
  - 未命中 → 新增。
- **notes（Jaccard 相似度）**：新内容与该用户已有 entries 逐条算 Jaccard 相似度（字符 2-gram 集合），**> 0.7 视为重复、跳过写入**。纯字符串计算，无 LLM、无向量。
- **profile**：覆盖式，无需去重。

### 4.3 容量上限（防无界增长）
- `preferences` ≤ 50 条 / 用户，超限淘汰 `updated_at` 最旧。
- `notes` ≤ 100 条 / 用户，超限淘汰 `created_at` 最旧。

## 5. 检索与注入

`prefetch(query)` 按 `user_id` 全量读取四类，拼成结构化块注入 system prompt。**无 embedding、无 query 相关性排序**——记忆量小，全量给。

```
<user-memory>
  <profile>偏好科技成长股，重视产业趋势…</profile>
  <preferences>
    - [看好] 光模块(sector)：AI算力需求拉动
    - [关注] 固态电池(concept)
  </preferences>
  <portfolio>中际旭创(300308.SZ)、新易盛(300502.SZ)</portfolio>
  <notes>
    [general] 用户提到年底前想减仓
  </notes>
</user-memory>
```

**截断策略**：拼装后若超 `MAX_PREFETCH_TOKENS`（2000，沿用现值），按优先级保留：profile → preferences → portfolio → notes（notes 最先被截）。

**空记忆**：无任何记忆时返回空块 `<user-memory></user-memory>`（与现有行为一致）。

## 6. 工具接口

扩展现有 `manage_memory` 工具（`memory/tool.py` + `builtin_provider.py:153-183` 的 schema）。

| 参数 | 变化 |
|------|------|
| `action` | 不变：`add` / `replace` / `remove` |
| `target` | **枚举新增 `preference`**：`notes` / `profile` / `preference` |
| `content` | 保留（notes/profile 用） |
| `old_text` | 保留（notes replace/remove 定位用） |
| `subject` | **新增**（preference 用，必填） |
| `stance` | **新增**（preference add 用，枚举） |
| `subject_type` | **新增**（preference 用，可选，默认 sector） |
| `reason` | **新增**（preference 用，可选） |

行为矩阵：

| target | add | replace | remove |
|--------|-----|---------|--------|
| profile | 覆盖式写 profile | 同 add | 不支持 |
| preference | 按 subject 去重写入 | 同 add（按 subject 更新） | 按 subject 删除 |
| notes | Jaccard 去重后追加 | 按 old_text 替换 | 按 old_text 删除 |

工具描述（prompt）需明确告诉 agent：**何时记 preference（用户表达对某板块/概念/个股的看好看空关注回避）vs profile（长期投资风格）vs notes（其他）**。

## 7. 自动抽取钩子（C 方案 — 留接口不实现）

- `sync_turn(user: str, assistant: str)` 保留方法签名，**本轮空实现**（`pass`）。
- 文档注释写明：未来可在此实现"mem0 式每轮 LLM 偏好抽取"——检索已有偏好 → 一次 LLM 从本轮交互抽取新偏好（告知已有的避免重复）→ Jaccard 去重 → 写入。
- 本轮偏好完全靠 agent 主动调 `manage_memory`。

## 8. 向后兼容与迁移

- 现有 `agent_notes` / `agent_profile` 中按 thread_id 存的历史数据**不迁移**——本就是坏的（绑在会话上），作废可接受。

- 集合名沿用 `agent_profile` / `agent_notes`，新增 `agent_preferences`。

## 10. 成功标准

1. 同一 `user_id` 在两个不同 `thread_id` 会话中，第一个会话写入的偏好能在第二个会话 prefetch 到（跨会话共享验证）。
2. agent 对同一 subject 二次表态 → preferences 中该 subject 只有一条（更新非堆积）。
3. 相似 note 二次写入 → 被 Jaccard 去重跳过。
4. 用户持仓出现在 prefetch 的 `<portfolio>` 块。
5. 无 user_id 的请求回退到默认用户，不报错。
6. 全部单元测试用 mock 通过，无需真实 Mongo。
