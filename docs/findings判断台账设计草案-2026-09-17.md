# Findings 判断台账设计草案 v0.1（2026-09-17）

> 目标：让 agent 在完成任务时能"主动挖出递进/变化/关联"，且**挖到的判断可沉淀、可复用、可溯源**。
> 解决三件事：**判断有据（历史）**、**不重复旧闻（新颖度）**、**结论可追（溯源）**。
> 状态：**讨论稿，未落代码。**

---

## 一、设计原则

1. **断言与判断分离**：`observation`（客观观察，append-only、可重算）≠ `finding`（判断，派生、可重算、可 supersede）。与 evidence 层"不可变真源 + 可重算投影"一致。
2. **主键是 (主体, 维度)**，不是 (实体, 关系)。**时间维度是一等公民**。
3. **阶梯是软约束**：prompt 里给 few-shot 参照，不强制枚举；台账存**原始措辞 + 可选归一化**，允许事后重算。
4. **一切锚 `evidence_id`**，判断必须能回指原文。
5. **去重靠水位线**，不靠人。

---

## 二、数据结构

### A. observation（观察记录 · append-only）

| 字段 | 说明 |
|---|---|
| `obs_id` | hash(evidence_id + subject + dimension + scope) |
| `subject` | `{ts_code, name, entity_id}`（公司为主，也可行业/指数） |
| `dimension` | 维度：`产线进展/客户认证/订单/产能/毛利率/开工率/客户导入/价格/政策/景气...`（种子词表 + agent 可扩展） |
| `dimension_scope` | 细化定位：`{product, production_line, counterparty, region}`（如"8英寸抛光硅片 / 三星"） |
| `stage` | `{raw: "已通过客户验证", normalized: "通过验证", level: 4, ladder: "客户认证"}` |
| `value` | 数值型维度：`{num, unit, period, metric, yoy, qoq}`（毛利率/订单金额/产能） |
| `statement` | 原文摘录（verbatim，供溯源与判断） |
| `certainty` | 确定性强度：`已/已批量 > 预计/拟 > 传闻`（措辞退化检测用） |
| `polarity` | positive / negative / neutral |
| `evidence` | `{evidence_id, doc_type, source_url}` |
| `event_date` / `published_at` | **双时间戳**（事件发生 vs 披露），递进与时效都依赖 |
| `extraction` | `{model, prompt_version, extracted_at}` |
| `written_by` | `pipeline` / `agent:{run_id}`（两个写入源都支持） |

**唯一键**：`(evidence_id, subject.ts_code, dimension, dimension_scope)` → 天然去重。

### B. finding（判断 · 派生可重算）

| 字段 | 说明 |
|---|---|
| `finding_id` | |
| `kind` | `progression`(递进) / `regression`(恶化) / `new_event`(新增事件) / `association`(关联挖掘) / `divergence`(矛盾/证伪) |
| `subject` / `dimension` / `dimension_scope` | 同 observation |
| `from` | `{stage, level, value, obs_id, date}` |
| `to` | 同上 |
| `delta` | `{stage_delta, value_delta, pct}` |
| `novelty` | `{is_first, first_seen_at, watermark_at_creation}` |
| `transmission` | 关联挖掘：`{via_entity, relation_type, hop, direction}`（如"经 TCL科技 传导"） |
| `supports` | `[obs_id...]` 支撑观察 |
| `contradicts` | `[obs_id...]` 矛盾证据 |
| `judgment` | agent 的结论文字（自然语言） |
| `confidence` | 0–1 |
| `status` | `candidate / verified / dismissed / superseded` |
| `supersedes` | 被本判断取代的 finding_id |
| `created_by` | `{task_id, agent_run_id, model, prompt_version}` |

### C. watermark（水位线 · 物化视图，可重算）

按 `(subject, dimension, dimension_scope)` 维护：
`max_level / max_value / first_reached_at / last_updated_at`。

**唯一职责：判定"这是不是新台阶"。**

---

## 三、核心机制：新颖度判定（防旧闻复读）

```
新 observation 到达
  ├─ level > watermark   → 生成 progression finding（is_first=true, first_seen_at=now）→ 更新水位线
  ├─ level == watermark  → 只记 observation，不产 finding        ← 去噪关键
  └─ level < watermark   → 生成 regression / divergence（低置信，待核验）
```

- 数值型维度（毛利率/订单额）：无 `level`，改用 **环比/同比变化 + 是否超出历史区间** 判定。
- **finding 去重**：若 `(subject, dimension, scope, kind, to.level)` 已存在且未 superseded → 只合并 `supports`，不新建。

## 四、走通一个例子（真实数据）

中晶科技 · 维度=产线进展 · scope=8英寸抛光硅片：

| 时间 | 观察 | 水位线 | 判断 |
|---|---|---|---|
| 2026-03-10 | "处于调试" level=3 | 3 | progression（首次） |
| 2026-06-15 | "增产上量" level=5 | 5 | **progression, is_first=true** ← 预期差 |
| 2026-09-16 | "处于增产上量和新客户认证阶段" level=5 | 5 | **== 水位线 → 不产判断** ← 去噪 |

> 这解释了为什么现在 `signals` 里同一件事重复出现——**它没有水位线**。

## 五、与现有系统的衔接

| 现有 | 处理 |
|---|---|
| Mongo `kg_evidence` | `observation.evidence_id` 直接引用，作为溯源锚点（保留） |
| Postgres `signals` | 视为粗糙的 `new_event` observation；长期**迁移/降级**为 observation 的一个来源，不再独立产"结论" |
| Neo4j | **仅用于 `transmission` 查询**（关联/传导），不再存事实；只取高置信边 |
| Qdrant `doc_chunks` | 用于 `history(subject, dimension)` 的语义召回 |
| 抽取管线 | 可继续写 observation（高置信低成本维度）；agent 写深挖维度——**同一张表、两个写入源** |

---

## 六、接口（agent 的工具面）

- `history_findings(subject, dimension?, scope?, before?)` → 按时间返回 observation + finding
- `search_findings(dimension, kind, since, status?)` → 跨主体扫描
- `write_observation(...)` / `write_finding(...)` → 写回（含 supports/evidence 校验）
- `watermark(subject, dimension, scope)` → 查水位线

---

## 七、评估指标（针对台账）

| 指标 | 含义 |
|---|---|
| 递进检出准确率 / 漏报率 | 人工标注子集 |
| 首次检出提前天数 | 比人工/市场早多久 ← 最贴近"预期差"价值 |
| 重复率 | 同一 finding 被重复产出（水位线是否有效） |
| 追溯完整率 | finding 是否都有 supports + evidence |
| 事件后表现 | N 日收益 / 盈利修正（回测） |

## 八、开放问题（待讨论）

1. **dimension 词表**：先给 8–10 个种子维度 + agent 扩展，周期性收敛；还是完全开放？
2. **阶梯是否物化**：先软（prompt few-shot），仅对高频维度物化 ladder？
3. **存储选型**：Postgres（唯一约束去重 + SQL 聚合水位线，倾向）vs Mongo（灵活，与 evidence 同库）？
4. **写入策略**：pipeline 与 agent 双写如何避免打架（以 agent 为高优先级 supersede？）
5. **矛盾处理**：口径不一致（不同产品线/不同期）算 divergence 还是分 scope 隔离？
6. **广度触发器**：要不要廉价扫描（词法/规则）来"发现用户没问到的"，还是纯 task-time？
