# 单仓强边界架构重构方案

> 日期：2026-08-18
> 状态：设计方案，待分阶段实施
> 背景：本机可能关机，云端需要持续沉淀数据和知识；同时 LLM 抽取、向量写入、Agent 推理需要从运行生命周期和代码边界上解耦。

## 一、结论

推荐采用“单仓库 + 强模块边界 + 独立 Worker 编排”的方案。

项目暂时不拆成多个仓库，也不立即改造成完整微服务。当前阶段更重要的是在同一个仓库内把不同生命周期的能力拆清楚：

```text
Data Foundation       原始数据采集与持久化
Evidence Fabric       Evidence 构建与证据队列
Knowledge Extraction  LLM / 向量 / 图谱抽取 Worker
Knowledge API         面向 Agent 的知识查询接口
Agent Runtime         本机 Agent 推理与交互运行侧
Ops                   启动、健康检查、备份、队列治理
```

核心原则：

```text
数据沉淀永远优先。
Evidence 构建不依赖 LLM。
LLM 抽取必须可暂停、可限流、可重试、可预算控制。
Agent 只调用 Knowledge API，不直接访问 Mongo/PostgreSQL/Neo4j/Qdrant。
服务器负责长期状态，本机负责交互、推理和实验。
```

## 二、为什么不直接拆微服务

当前腾讯云服务器规格为 4 核 CPU、8GB 内存、120GB SSD、10Mbps 带宽。它适合小规模、低并发、长期运行的知识底座，但不适合一次性承载复杂微服务体系。

完整微服务拆分会立刻引入：

- 多套镜像构建和发布流程。
- 多服务认证、网络、配置、健康检查。
- 更多容器常驻内存。
- 更复杂的数据迁移和兼容成本。
- 更高的线上排障复杂度。

因此，近期不建议拆 repo，也不建议把 data service、knowledge service、agent service 全部独立部署。更稳妥的路径是在单仓内先形成硬边界，等系统稳定、接口收敛后，再评估是否拆服务。

## 三、目标运行架构

```text
本机电脑
  Agent Runtime
  Frontend Dev
  Prompt / Tool / Report 调试
  临时实验脚本
        |
        | HTTP API
        v
腾讯云服务器
  Knowledge API
  Data Scheduler
  Ingestion Job Worker
  Evidence Builder
  Controlled Extraction Workers
  PostgreSQL / MongoDB / Neo4j / Qdrant
```

云端必须能够在本机关机后继续运行：

- K 线同步。
- 公告采集。
- 互动易采集。
- 新闻、研报等低频同步。
- 原始数据入库。
- Evidence 构建和排队。
- Knowledge API 查询。
- 健康检查和队列观测。

本机可以随时关闭：

- Agent 推理会话。
- 前端开发服务。
- Prompt 调试。
- 实验性脚本。

## 四、模块边界

### 4.1 Data Foundation

职责：

- 调度 K 线、公告、互动易、新闻、研报等数据采集。
- 管理 `ingestion_jobs` 这类原始采集任务。
- 把原始业务数据写入 PostgreSQL。
- 记录同步状态、失败原因和重试次数。

不负责：

- 调用 LLM。
- 写 Neo4j。
- 写 Qdrant。
- 生成投资结论。

代码上对应当前 `backend/app/data_pipeline`、`backend/scripts/ingestion_worker.py`、部分同步脚本。后续应逐步把它收敛成纯数据采集层，不直接感知知识抽取细节。

### 4.2 Evidence Fabric

职责：

- 从公告、互动易、研报、新闻等原始数据中构建 Evidence。
- 写入 MongoDB `kg_evidence`。
- 生成 `kg_extraction_jobs`。
- 做低成本规则过滤、去重、切块、来源追溯。

不负责：

- LLM 抽取实体/关系。
- 写 Neo4j。
- 写 Qdrant。
- 直接服务 Agent 推理。

Evidence Fabric 必须是机械构建层。即使 LLM API 不可用、余额不足或向量库异常，它也应该继续稳定沉淀 Evidence。

### 4.3 Knowledge Extraction

职责：

- 消费 Evidence extraction jobs。
- 对不同任务类型使用独立 worker：
  - `combined`：LLM 抽取实体、关系、结构化事实。
  - `vector`：向量化 Evidence chunk，写 Qdrant。
  - `signal`：规则或模型信号抽取。
- 写 Neo4j、Qdrant、MongoDB extraction status。
- 管理重试、失败分类、限流和预算。

Knowledge Extraction 是昂贵且可降级的层。它可以暂停、限速、夜间运行或按优先级运行，但不能影响 Data Foundation 和 Evidence Fabric。

后续需要补齐的队列状态：

```text
pending   等待处理
running   正在处理
done      已完成
skipped   规则判断无须抽取
failed    可重试失败达到上限
blocked   外部条件阻塞，例如 LLM 余额不足或模型服务不可用
dead      数据异常或不可恢复失败
```

### 4.4 Knowledge API

职责：

- 给 Agent 提供稳定、少量、高层的知识查询接口。
- 聚合 Evidence、图谱、结构化事实、行情和来源追溯。
- 隐藏底层 PostgreSQL、MongoDB、Neo4j、Qdrant 差异。

优先接口方向：

```text
研究一个公司
研究一个产业链或产品链
研究一个主题或行业
自然语言搜索研究上下文
追溯 evidence_id 原文
检查知识底座 readiness
```

Agent 不应该直接面对大量底层数据库查询工具，也不应该直接连接云端数据库。生产路径应统一走 HTTP API。

### 4.5 Agent Runtime

职责：

- 本机运行 Agent 推理。
- 组合工具、Prompt、报告生成、前端交互。
- 调用云端 Knowledge API 获取上下文。
- 保留本地开发 fallback，但生产路径不直连数据库。

不负责：

- 常驻采集任务。
- Evidence 批量构建。
- LLM 知识抽取队列消费。
- 长期存储状态。

### 4.6 Ops

职责：

- 云端启动脚本。
- Docker Compose profiles。
- 健康检查。
- 队列观测。
- 数据备份和恢复。
- 配置检查。
- 日志诊断。

Ops 层应该能回答这些问题：

- K 线最新日期是什么？
- 公告和互动易是否还在入库？
- Evidence 待抽取数量是多少？
- LLM worker 是否开启？
- 哪些 job 失败最多？
- 当前是否因为 LLM 余额、API、Qdrant、Neo4j 阻塞？

## 五、关键数据流

### 5.1 原始数据沉淀

```text
Scheduler
  -> enqueue ingestion_jobs
  -> Ingestion Job Worker
  -> PostgreSQL 原始业务表
```

该链路是最高优先级。它必须尽量少依赖外部昂贵服务。

### 5.2 Evidence 构建

```text
PostgreSQL 原始数据
  -> Evidence Builder
  -> MongoDB kg_evidence
  -> MongoDB kg_extraction_jobs
```

Evidence 构建可以跟随数据采集自动运行，也可以由定时任务批量补跑。但它不应该调用 LLM。

### 5.3 知识抽取

```text
kg_extraction_jobs
  -> combined worker
  -> LLM API
  -> Neo4j / MongoDB status

kg_extraction_jobs
  -> vector worker
  -> Embedding API
  -> Qdrant / MongoDB status

kg_extraction_jobs
  -> signal worker
  -> rule/model signal extraction
  -> MongoDB / PostgreSQL / Neo4j
```

这条链路应支持手动开关、低并发、失败隔离和预算控制。

### 5.4 Agent 查询

```text
Local Agent Runtime
  -> Cloud Knowledge API
  -> PostgreSQL / MongoDB / Neo4j / Qdrant
  -> Research Context
  -> Agent 推理和报告
```

Agent 拿到的是研究上下文，不是底层存储细节。

## 六、LLM 与向量接入策略

真实 API Key、Base URL、模型名和代理信息只能放在服务器 `.env` 或安全配置中，不进入 Git。

建议配置项：

```text
LLM_BASE_URL=
LLM_API_KEY=
LLM_MODEL=
LLM_TIMEOUT_SECONDS=60
LLM_MAX_CONCURRENCY=1
LLM_DAILY_BUDGET=

EMBEDDING_BASE_URL=
EMBEDDING_API_KEY=
EMBEDDING_MODEL=
EMBEDDING_DIMENSION=
EMBEDDING_MAX_CONCURRENCY=1
```

运行策略：

- LLM worker 默认关闭。
- 明确开启时才消费 `combined` jobs。
- 每轮处理数量有限制。
- 遇到余额不足、限流、认证失败时，把 job 标记为 `blocked`，而不是反复失败重试。
- Evidence 和原始数据采集不受 LLM 状态影响。
- 向量 worker 与 LLM worker 分开运行，避免 embedding 故障影响实体关系抽取。

## 七、部署 Profile

建议新增或逐步演进以下运行 profile：

```text
cloud-base
  postgres
  mongo
  neo4j
  qdrant
  backend

cloud-ingestion
  scheduler
  job-worker
  evidence-builder

cloud-extraction
  combined-worker
  vector-worker
  signal-worker

local-agent
  frontend
  agent-runtime
```

当前 `server_start.sh` 可以继续作为云端入口，但后续应把 profile 和 worker 类型表达得更明确。

默认云端启动策略：

```text
cloud-base:       enabled
cloud-ingestion:  enabled
cloud-extraction: disabled by default
local-agent:      disabled
```

当确认 LLM API、预算和队列策略后，再手动开启 `cloud-extraction`。

## 八、代码调整原则

后续实施时按以下原则推进：

- 不做一次性大重构。
- 先增加边界和配置，再移动代码。
- 先让现有功能继续跑，再逐步收敛接口。
- 每次只处理一个层之间的耦合点。
- 关键路径补测试，尤其是 scheduler、worker、queue status、API fallback。

优先处理的耦合点：

1. `scheduler` 不再直接运行 LLM 抽取。
2. Evidence 构建与 LLM 抽取拆成不同进程或不同命令。
3. `combined`、`vector`、`signal` worker 独立配置和独立启动。
4. Agent 知识工具从直连数据库改为调用 Knowledge API。
5. 增加队列治理 API 或脚本。

## 九、分阶段实施

### Phase 1：稳定云端基础盘

目标：电脑关机后，数据采集和 Evidence 沉淀继续运行。

范围：

- 固化 `server_start.sh` 的云端默认行为。
- 确认 scheduler、job-worker、backend、数据库长期运行。
- Evidence 构建保持低成本、无 LLM 依赖。
- 增加一键健康检查输出。

成功标准：

- K 线、公告、互动易可以持续入库。
- Evidence 队列可以增长和观测。
- LLM 关闭时系统没有错误刷屏。

### Phase 2：硬化队列和 Worker 边界

目标：昂贵抽取任务可控运行。

范围：

- 拆清 `combined`、`vector`、`signal` worker。
- 增加 `blocked` 状态。
- 增加失败原因分类。
- 增加并发、批量、预算、时间窗口配置。
- 增加队列统计命令。

成功标准：

- LLM 余额不足不会制造无意义重试。
- 可以只跑 vector 或只跑 combined。
- 可以精确看到每类 job 的 backlog。

### Phase 3：Agent 只走 Knowledge API

目标：本机 Agent 与云端数据库解耦。

范围：

- 梳理 Agent 当前知识工具。
- 为高频研究场景补 Knowledge API。
- 把 Agent 工具从数据库直连迁移为 HTTP 调用。
- 本地直连仅保留为开发 fallback。

成功标准：

- 本机只需要云端 API 地址和认证信息即可运行 Agent。
- 数据库端口不需要暴露给本机 Agent。

### Phase 4：代码模块整理

目标：让包结构和职责边界一致。

范围：

- 收敛 `data_pipeline` 内部的知识抽取调用。
- 收敛 `knowledge` 内部的 Evidence、Extraction、API 子模块。
- 收敛 `reasoning` 对知识层的依赖。
- 为跨层调用建立接口层。

成功标准：

- 新人能从目录结构判断模块职责。
- 修改 LLM worker 不影响数据采集。
- 修改 Agent 工具不影响 Evidence 构建。

### Phase 5：运维化

目标：让云端长期可维护。

范围：

- 备份 PostgreSQL、MongoDB、Neo4j、Qdrant。
- 增加云端诊断脚本。
- 增加日志和错误分类。
- 增加队列治理命令。
- 收敛安全配置和端口暴露策略。

成功标准：

- 可以快速判断“数据没跑”、“队列堵了”、“LLM 挂了”、“向量库挂了”是哪一类问题。
- 可以恢复关键数据库。
- API Key 和数据库密码不进入仓库。

## 十、近期最应该做的事

接下来最应该按这个顺序推进：

1. 先补云端健康诊断：数据日期、ingestion job、evidence job、worker 开关、LLM 配置状态。
2. 再补队列治理：`combined`、`vector`、`signal` backlog、失败分类、blocked 状态。
3. 然后接入用户提供的 LLM API 和 URL，但只写入服务器 `.env`。
4. 小批量开启 `combined` worker，先从互动易低价值过滤后的样本开始。
5. 最后迁移 Agent 工具到 Knowledge API。

这套顺序能先保证数据不会断，再逐步恢复知识抽取能力，最后完成本机 Agent 与云端知识底座的运行解耦。
