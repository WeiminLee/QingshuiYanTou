## 3. LLM 抽取慢的根因诊断（2026-09-04 定位）

**注意拓扑**：LLM 抽取跑在**云端 scheduler**（`app/data_pipeline/scheduler.py` 的 `_run_evidence_worker_job`，每 30s，APScheduler max_instances=1），不是 d 集群 GPU 机。d 集群只做 embedding + PDF 下载。

**根因链**：

1. **抽取模型选错**（云端 `.env`：`LLM_EXTRACTION_MODEL=minimax-m2.7` —— 推理模型）。原设计是 flash 快模型（`deepseek-v4-flash`），因其 403 下线临时换成 minimax-m2.7。
2. **thinking 泄漏**：`extra_body={"thinking":{"type":"disabled"}}` 对 minimax-m2.7 没生效，模型复述原文，流式总超时兜底（`llm_client.py:104`，180s）频繁触发 → 日志反复出现 `LLM stream total timeout 180s`。
3. **JSON 解析失败链**：输出被 thinking 污染 → 首轮 JSON 校验失败 → JSON 约束重试 → 简化 prompt 重试（每 chunk 最多 3 次慢调用）。
4. **单实例调度**：APScheduler `maximum number of running instances reached (1)` 高频跳过；白天并发 `EVIDENCE_CONCURRENCY_DAY=8`（夜间 16）。
5. 单条 combined 实测耗时 23s ~ 234s 不等。

**pjlab 网关当前可用模型**（`GET /models`）：`glm-5.3-flash`、`deepseek-v4-flash` / `-0731`（已重新上架）、`glm-5.2/-1m/5.3`、`qwen3.8-27b-fp8`、`Qwen3.6-35B-A3B-FP8`、`kimi-k2.6/k3`、`minimax-m2.7`、`intern-s1`、`Intern-S2-Preview-397B`。

**处置方案（已完成诊断，未执行）**：

1. 首选：云端 `.env` 改 `LLM_EXTRACTION_MODEL=glm-5.3-flash`（或 `deepseek-v4-flash`/`qwen3.8-27b-fp8`）→ `systemctl restart qingshui-scheduler.service`。
2. 换非推理模型后，thinking 关闭问题自然规避。
3. 之后再视情况提并发/启用独立 evidence worker（`EVIDENCE_WORKER_ENABLED=0` 现关着）。
