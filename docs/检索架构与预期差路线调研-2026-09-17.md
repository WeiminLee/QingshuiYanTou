# 检索架构与预期差路线调研（2026-09-17）

> 背景：讨论"是否放弃 KG/重抽取管线、转向 agentic search"，并澄清系统核心价值"预期差挖掘"的技术含义。
> 结论先行：**检索是证据层，不是核心；预期差的本质是"状态在时间轴上的演进"，需要「可检索的历史 + 可写回的判断台账」，而非重预计算图谱。**

---

## 一、行业最佳实践（2026 共识）

**1. 不是"grep vs 向量"，是分层 + 混合**
- PwC 论文《Is Grep All You Need? How Agent Harnesses Reshape Agentic Search》(arXiv 2605.15184)：10 个 harness×模型组合下，**inline 返回结果时 grep 全胜向量**；改为 **file/指针式返回后 5/10 反转**。
- **返回方式造成的分差（最大 37.9pp）> 检索器本身分差（1.7–23.3pp）**；换 harness 分差 16.4pp。
- 结论：**harness + 结果呈现方式是"被测系统的一部分"**，必须固定后本地实测，不能只比检索器。

**2. 规模决定形态**
- DCI（直连语料 grep，arXiv 2605.05242）：69%→80%、成本更低，但 **100k→400k 文档即退化**。
- 有界工作区（RISE arXiv 2606.06880、Dr-DCI arXiv 2606.14885）：先检索划界、再在界内 grep；RISE-BM25 约等于纯 DCI、**成本 1/4**；1M 文档时 RISE 81%、纯 DCI 崩。
- RARG（arXiv 2607.24223）：把相关性当"执行先验"——按 embedding 相关性排序文档再 grep、再 rerank 命中片段。
- **本项目文档量 30 万+ → 纯 grep/DCI 单干会退化，应采用"语义召回划界 → 界内 grep/精读"的 hybrid bounded workspace。**

**3. 决策规则（生产实践）**
- 先建 **eval set + router**，其余优化建立在其上。
- corpus > 1M tokens 且 > 1000 查询/天 → 必须走检索；**Postgres + pgvector + 全文检索即可，无需独立向量库**。

## 二、中文全文检索选型（针对本项目）

| 方案 | 结论 |
|---|---|
| PG 内置 FTS | 默认不支持中文分词，需扩展 |
| **zhparser (SCWS)** | 官方推荐中文分词；需**自定义领域词典**（公司简称/产品名） |
| **pg_trgm** | 对短串（"中晶科技""003026.SZ"）极好；长文本精度不足 |
| ES + IK | 中文效果最好，但多一套中间件运维 |
| 选型共识 | 数据在 PG、量 < 千万、带过滤条件、要强一致 → **PG FTS 优先**；海量/高并发/复杂相关性才上 ES |

**建议**：自建 docker 可控 → **zhparser(tsvector) + pg_trgm 混合**。

**必踩的坑**
1. 索引表达式必须与查询表达式**逐字一致**才走索引 → 用 **GENERATED 生成列**。
2. 建索引用 `english`、查询用 `simple` = 永远匹配不上，两边配置必须一致。
3. **分词配置/词典变更后，历史 tsvector 不会自动重算**，必须 rebuild。
4. 单条 document 别 > 10MB（性能显著下降）→ 长研报必须切分。

## 三、评估方法（当前最大缺口）

- **没有 gold set，任何方案对比都是空谈。**
- 检索指标：**Recall@k 首要**（k 必须=实际喂给模型的量）；其次 Precision@k / MRR / nDCG。
- gold set：150–300 条真实查询，分层（单点/多跳/对比/歧义）+ **hard negatives**（同实体不同期、同产品不同公司）。
- 合成数据陷阱：LLM 从 chunk 反写问题会照抄措辞 → 分数虚高；`answer-in-chunk` 泄漏；近重复 chunk 污染 → 必须人工抽审。
- **agentic 特有**：必须**固定 harness 与结果呈现方式**再比。
- 消融顺序：先 recall（chunking/embedding/hybrid），再 ranking（rerank）。
- 本项目特殊性：投研常无唯一正确答案 → 更贴合 **citation accuracy**（引用是否指向真实且支持 claim 的 passage）+ **faithfulness**；监控场景则看 **coverage/漏报率**。

## 五、预期差的重新定义与分析（本次讨论核心）

**用户澄清**：预期差**不是相对某个基准的偏离**，而是：
- 互动易中产线进展的**递进式表达**
- 公告中产品毛利率的**增加**
- 认证进展的**措辞变化**
- 行业利好新闻发布
- 关联公司公告中的大订单签订

**归纳**：预期差 = **同一主体、同一维度的状态在时间轴上的正向/负向演进**（尤其是首次跨越新台阶）。

| 例子 | 主体 | 维度 | 阶梯（状态机） |
|---|---|---|---|
| 产线进展递进 | 公司 | 产线进展 | 规划→建设→调试→试产→小批量→量产 |
| 毛利率增加 | 公司×产品 | 毛利率 | 数值序列 40%→45% |
| 认证措辞变化 | 公司×产品 | 客户认证 | 送样→验证中→通过→批量供货 |
| 行业利好 | 行业 | 景气 | 新增事件 |
| 关联公司订单 | 关联公司 | 订单 | 新增/金额跃升 |

**这意味着**
- 核心原语是 **(主体 × 维度) 的状态时间线**，不是"实体-关系"静态图。
- **agentic search 解决"读得准"，解决不了"递进"**——递进是跨时间的，单次 agent 只看一个文档。
- **没有历史对照，就无法判断"这是新台阶"**：维护不是可选后处理，而是判断的必要输入。

## 六、架构结论

**主干**：agent 的判断与关联挖掘（task-time，核心能力所在）。
**substrate（最小必需，不是重 KG）**：
1. **可检索的历史**：按 (主体, 维度, 时间) 取回过往表述/数值。
2. **判断台账（findings ledger）**：agent 挖到的判断写回 —— **维护是 agent 作业的沉淀物，不是独立批处理管线**。

```
用户任务 / 新闻点
  → 召回证据（检索）
  → 拉该主体该维度的历史（工具）
  → 判断：递进？变化？关联？（LLM 核心）
  → 写回台账（维护·副产品）
  → 下次判断自动有据
```

**对既有架构的修正**
- 之前"KG 可退役"的说法需修正：**传导差是预期差的重要来源**，但 KG 应从"事实真值"降级为**高精度、可维护、可审计的传导骨架**。
- 阶梯（状态机）不必预建完整：先写进 prompt 当 few-shot 参照（软约束），台账存原始措辞 + 可选归一化。

**诚实的代价**
1. 一致性/可重算差 → 台账保留原文证据，允许事后重算。
2. 防重复/防矛盾 → 必须按 (主体, 维度, 阶段) 去重 + 保留首次时间（新颖度的唯一实现）。
3. 传导体量 → 只做高精度小范围，宁缺勿错。
4. **广度盲区** → 纯 task-time 只能挖"用户问到的"；若要"发现用户没想到的公司"，需极廉价触发器（词法/规则扫全市场 → 命中才叫 agent 下钻）。
5. 成本/延迟/非确定性 → trace + 缓存 + 结果复用（台账即复用载体）。

---

## 七、需要深挖的点（按优先级）

1. **findings 台账 schema**（最关键，见另文草案）。
2. **(主体, 维度) 历史检索**：如何从 evidence + 台账稳定取回"这家公司在这个维度上以前怎么说的"。
3. **判断的一致性**：prompt 阶梯参照如何给，才能让两次判断可比。
4. **关联挖掘的触发与落点**：一个新闻点 → 该挖哪些主体（事件→实体映射）。
5. **广度廉价触发器**：要不要做、用什么做。
6. **评估**：人工标注"真递进/真关联" + 事件后表现。

---

## 八、中间过程注意事项（避坑清单）

- 别一次性重构：先建 eval + 新老双轨 A/B，证明替代更优再退役。
- 证明责任在"新方案"：新方案必须在本项目语料上打赢现有向量，才配取代。
- 固定并记录 trace（router 选了哪条路、呈现方式），否则无法调优边界。
- 防 context pollution：多轮检索结果跨轮去重 + rerank + 截断。
- 防幻觉引用：引用必须可回指真实 passage_id（evidence_id 天然锚点）。
- 中文分词需领域词典（否则"中晶"被切成"中/晶"）。
